[doorplate](https://github.com/jeremeybingham/doorplate) 0.6.2 is out. It is still an alpha: an open-source US address parser written in Rust, with a
[Python package](https://pypi.org/project/doorplate/) and a [command-line tool](https://crates.io/crates/doorplate-cli). Like 0.6.1 it is a speed release:
a parse takes about 25% less time, and no key, field or warning it returns has changed. The `k5` key stays.

This is a short post. The long one, on how I keep rule changes and speed changes apart and why the accuracy benchmarks have stopped moving, is the
[0.6.1 post]({{ site.baseurl }}/2026/11/13/doorplate-0-6-1.html). Here: what got faster, and where doorplate goes next.

*doorplate parses and formats addresses. It does not validate that an address exists or can receive mail.*

## What changed since 0.6.1

- **24.6% less time per parse.** On one pinned CPU with the first 4,000 everyday addresses of the benchmark suite, three alternating rounds beside a rebuilt
  0.6.1: 7.93 µs became 5.98 µs, which is 1.32 times the parses a second. In instructions it is 25.1% fewer (62,696 to 46,986 per parse), and allocations
  fell from 39.3 to 23.9 per parse. On the suite's own speed run, `parse_tokens` went from 82,331 to 98,830 parses a second on one thread, and Python
  `parse` from 123,826 to 150,949.
- **The command line starts faster.** One `doorplate parse` call takes 0.73 ms instead of 3.4 ms, and 100,000 lines through it take 1.24 s instead of 2.03 s.
- **Nothing else.** The `ParsedAddress` for all 76,421 public suite inputs is byte-identical to 0.6.1's, and over 36.9 million rows from seven public data
  sets not one key, unit key, unit field or warning differs. The accuracy runs give the 0.6.0 figures again.

The same two rules held as in 0.6.1: a speed change must change nothing, and it stays only if it clears a bar, now 0.5% of instructions (it was 2%; the
easy gains are gone), with related small changes counted together.

## Where the time went

A fresh profile after 0.6.1 gave eight groups of changes. In order of what they saved:

- **Find words with a hash, not a search.** The street-suffix, unit, state, highway, directional and special tables, and the place table, are found through
  an open-addressing hash index instead of a bloom test and a binary search (−6.8% and −3.5% of instructions). Still no dependency.
- **Do less in the tokenizer.** Byte scans instead of character searches for trimming, one pass from the end to find each segment's edge (−5.6%), and
  unit and highway readings, or a city string for every possible cut, built only where the result can be used (−5.2%).
- **Fewer allocations.** A joined run of words is built on the stack when it fits in 64 bytes, and some helpers read slices instead of collecting vectors (−2.6%).
- **Reject early.** The placeholder and building-word checks return from the first byte of the text (−1.7%), plus a guard in the suffix lookup (−1.4%).
- **Tables built at compile time.** The place index and the ZIP prefix table are written by `build.rs` instead of built on the first parse. The first parse
  in a process takes 0.95 million instructions instead of 17.8 million. That barely shows in a long batch (−1.8% on 20,000 parses), but it is most of the
  difference for a command-line call or a short Python script.
- **The command line writes JSON directly.** `doorplate parse` built an object tree and then serialized it; it now writes each record straight to a buffer (−39%, same bytes out).

The cost is size: the command-line binary grows from 5.2 to 6.7 MB and the wheel from 2.1 to 2.5 MB, because the tables are now built into the program.
Every step is listed with its figure in the [changelog](https://github.com/jeremeybingham/doorplate/blob/main/CHANGELOG.md).

## The release cycle, with 0.6.2

![Rules in, then the speed back. Whole-suite accuracy (suite v1) from 0.3.1 to 0.6.2: 92.2, 92.3, 92.3, 93.4, 93.4, 94.4, 94.4, 94.4%. Time per parse in microseconds: 25.8, 21.1, 21.0, 23.2, 10.6, 11.2, 8.10, 5.98. Accuracy steps up at 0.5.0 and 0.6.0, which are slower than the release before; 0.5.1, 0.6.1 and 0.6.2 win the time back.]({{ site.baseurl }}/assets/doorplate-0-6-2-cycle.png)

A `0.x.0` release adds rules, accuracy goes up and a parse gets a little slower; the point releases after it win the time back without touching a key.
0.6.2 is the second of those after 0.6.0. Compared with the first release in the chart, a parse now needs less than a quarter of the time it did in 0.3.1 (5.98 against 25.8 µs).

One caution about the chart: 0.3.1 to 0.6.1 were built and timed together on 2026-11-13, and 0.6.2 was measured at its release commit the next day. The
same method and machine, but not the same session, which is why the 24.6% above comes from the pair measured side by side (the 0.6.1 bar is 8.10 µs in
one session and 7.93 in the other). The 3.4 times fewer instructions against 0.4.1 in the top graphic is a count, not a timing, so it does not depend on the day.

The accuracy lines are flat across 0.6.1 and 0.6.2 because no output changed; that is the point of the release. Why the benchmarks are flat even across
releases that do change output is the subject of the 0.6.1 post.

## What comes next: 0.7.0, the first beta

0.7.0 is planned as the first **beta**. The plan is in the [roadmap](https://github.com/jeremeybingham/doorplate/blob/main/docs/roadmap.md), in the order it ships:

1. **Remove the state packs.** doorplate has carried a separate data structure for state-specific data, and today Florida is its only user. Its rows fold into
   the ordinary place list and base tables, and `state_data_version` leaves the diagnostics, the Python package and the JSON provenance. This is the last
   API break I plan: no key and no parse output changes.
2. **Puerto Rico.** Addresses there have shapes the rest of the country mostly lacks (the street before the number, as in `CALLE DEL SOL 210`, and `URB`
   urbanization lines), and they are under-served today. The first step is research on real examples, then rules.
3. **More accuracy rules.** The rules that change what an input produces, each one measured against the frozen `k5` keys and picked by the number of real
   rows it affects, as described in the 0.6.1 post. Since they change keys, 0.7.0 brings a new key version, `k6`.
4. **The beta itself.** The notices that say "alpha" change, and the promises start: from 0.7.0 the API surfaces and warning codes are stable, and a
   rename or removal is announced one release ahead. A new key version would come only in a minor release (0.8 and later), never in a patch.

The beta needs items 1 and 3 done and the `k6` measured on the private sources. Puerto Rico does not have to be finished: a rule that misses the release moves to 0.8.

Priorities follow the data people bring, so real, messy addresses still help most. `doorplate anonymize` keeps the shape of an address and changes the
digits and names, so you can send some without sending the addresses. The [parser showdown](https://github.com/jeremeybingham/address-parser-showdown) comparison
is separate from all of this and has its own report.

## What this does not prove

The figures here are measured on one machine (an Intel Core i9-9900K under WSL2, pinned to one CPU) and one address mix, not promises about yours. The
[speed page](https://github.com/jeremeybingham/doorplate/blob/main/docs/speed-and-size.md) and the
[benchmarks page](https://github.com/jeremeybingham/doorplate/blob/main/docs/benchmarks.md) have every figure with its build and method.
