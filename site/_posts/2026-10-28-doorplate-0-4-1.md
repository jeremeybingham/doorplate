[doorplate](https://github.com/jeremeybingham/doorplate) 0.4.1 is out. It is still an alpha, and it is still an open-source US address
parser written in Rust, with a [Python package](https://pypi.org/project/doorplate/) and a
[command-line tool](https://crates.io/crates/doorplate-cli). When I announced [0.4.0]({{ site.baseurl }}/2026/10/21/introducing-doorplate.html) I said
what it needs most is real, messy addresses. The honest problem with that request is that the best messy addresses are private. This release
is my attempt to fix that part: `doorplate anonymize`.

*doorplate parses and formats addresses. It does not validate that an address exists or can receive mail.*

## What is new

- **`doorplate anonymize`** (also `doorplate.Anonymizer` in Python and `doorplate::Anonymizer` in Rust): rewrites address-like text so it can go
  into a bug report. The digits and the names change; the shape stays. More below.
- **Your own spellings and places.** A custom layer loads local suffix spellings, unit words, directionals, places and ZIPs on top of the shipped
  tables, from the command line, Python or Rust, without a fork ([the guide](https://github.com/jeremeybingham/doorplate/blob/main/docs/custom-layers.md)).
  Without a layer, parsing is unchanged.
- **`doorplate.compat`**, a usaddress-shaped module: `import doorplate.compat as usaddress` gives you `parse`, `tag` and `RepeatedLabelError`
  for code that already speaks that library.
- **Faster columns.** `parse_column` for pandas and Polars, and the DuckDB functions, now build their results in Rust.
- **A documentation site** at [doorplate.readthedocs.io](https://doorplate.readthedocs.io/), with a Python reference and a command-line reference.

No parser rule and no match key changed since 0.4.0: I compared keys and warnings row by row against 0.4.0 on about 37 million rows from seven
sources and found no difference, so stored `k3:` keys stay valid. The [changelog](https://github.com/jeremeybingham/doorplate/blob/main/CHANGELOG.md)
has the full list.

## Sharing a sample of private data

Say you have a county export, a mailing list or an old database, and doorplate gets some rows wrong. You cannot post the rows, and rewriting them
by hand is slow and easy to get wrong. The anonymizer does the mechanical part, and it works on lines that do not parse, which are the ones you most
want to report.

```sh
doorplate anonymize in.csv --column line1 --column line2 --column zip -o shareable.csv
```

For each value it keeps what decides how a parser reads a line, and replaces what identifies a place or a person. Here is a real run on invented
rows (`--seed 7`, which you should leave out for real data):

| Before | After |
|---|---|
| `123 N Zephyrmill Ave Apt 4`, Miami FL 33101 | `316 N Hadujapigu Ave Apt 3`, Miami FL 33116 |
| `PO Box 1234`, Austin TX 78701 | `PO Box 9070`, Austin TX 78775 |
| `RR 2 Box 15`, Dalton GA 30720 | `RR 7 Box 24`, Dalton GA 30739 |
| `88 Bayview Dr Ste 200`, line 2 `ATTN Pat Quinn` | `98 Mivodig Dr Ste 529`, line 2 `ATTN Vup Talul` |
| `41-20 Bayview Ave`, Flushing NY 11355 | `24-39 Mivodig Ave`, Flushing NY 11395 |

Digit runs become other digits of the same length. Words the parser knows (suffixes, directionals, unit words, states, `PO BOX`, `RR`) stay. Any
other word becomes an invented one of the same length and case. The same value gets the same replacement within a run, so duplicates stay
duplicates. The tool also parses each value before and after and tells you how many the parser reads the same way, which answers the question that
matters: will the bug I saw in the original still show up in the copy? On street lines from nine real sources, 96.7% to 99.9% of values read the
same afterwards, and no digit run stayed as it was.

### What it does not do

**It is obfuscation that keeps the shape. It is not anonymity.** Read the output before you send it.

- Words the parser knows stay, so a street called `Harbor` or `Park`, or a person named `Lane`, is unchanged.
- The city, the state and the first three ZIP digits stay. With a rare street shape, that can narrow a record to a small area.
- It cannot tell a name from any other unknown word, and it does not know what is sensitive in your data.
- A seed you publish lets anyone test a guess, so for real data run it without `--seed`.

### How to send a sample

1. Run `doorplate anonymize` with no `--seed`.
2. **Read the output.** Search it for the names you know are in the file, and look at the values it reports as not the same.
3. Send a small sample, not the file. Ten lines that show the problem are worth more than ten thousand.
4. [Open an issue](https://github.com/jeremeybingham/doorplate/issues/new?template=misparse-or-messy-data.md) with the lines and what you expected.
   If it still feels too close to real data, describe the shape in words and send counts.

The details, the limits and the Python and Rust versions are in
[the anonymizing guide](https://github.com/jeremeybingham/doorplate/blob/main/docs/anonymizing.md).

## What I would most like to see

These are shapes that doorplate reads wrongly or is unsure about, from reviewing real rows by hand (the examples here are invented). If your data has
any of them, a sample would help:

- **Care-of text at the start of a line with no comma**, `C/o Dana Quill 22 Fernhill Ave Apt 3B`, which currently swallows the whole line.
- **A letter before the house number**, `W 6120 22nd Ave`, and grid numbers such as `N45 W2210 Oak Ave`.
- **Rural routes and boxes written oddly**: `RR4 BOX 88`, `HRC 5 BOX 12M`, a box before the street.
- **A hyphen before the unit or the place**, `7410 NW 52nd St - 2210`.
- **Puerto Rico street-first forms** with `CALLE`, `URB` and lot codes.
- **Text written twice**, a line repeated or a city, state and ZIP repeated at the end of line 1.
- **Queens-style numbers written with a space** instead of a hyphen, `31 14 90th Ave`.

The [open issues](https://github.com/jeremeybingham/doorplate/issues) list each one with counts, and every fix needs a source, an invented test case and a
before-and-after measurement before it ships.

## The numbers, with the caveats

On the benchmarks in the repository (whole address right, coarse labels), measured on 0.4.0 and unchanged in 0.4.1:

| | doorplate | usaddress |
|---|---|---|
| Benchmark suite, `natural` stratum (16,001 addresses) | 98.3% | 96.1% |
| Benchmark suite, whole suite (19,586) | 92.3% | 85.5% |
| Geocode benchmark, `dev` split | 94.5% | 88.1% |
| usaddress's own regression tests | 99.2% | **100.0%** |
| Addresses per second, one thread | 38,305 | 8,937 |
| Addresses per second, `parse_many`, 4 threads | 152,376 | (no batch call) |

usaddress wins on its own tests, as you would expect; the gap there shows where the two choose differently, not an accuracy contest. The suite is my
own, built from public National Address Database rows and frozen, with its blind spots left in on purpose. The two libraries also do different jobs:
usaddress labels tokens, and doorplate also produces USPS Publication 28 and RESO output, a match key and warnings. The
[benchmarks page](https://github.com/jeremeybingham/doorplate/blob/main/docs/benchmarks.md) has the full tables and how to rerun them.

## What is next

0.4.1 is an alpha, so the match key is versioned (store the `k3:` prefix with your keys), and names in the API and the warning codes may still change
before 1.0. The next key-changing release, `k4`, will fix the shapes above, one at a time, as samples and evidence come in. If doorplate gets your
addresses wrong, that is the most useful thing you can tell me.
